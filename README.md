## Overview

This project builds a market-risk analytics framework for a multi-asset portfolio, in the spirit of a bank risk-analytics team's toolkit. It combines two things:

1. **A general market-risk pipeline** (Part 1) — volatility forecasting, VaR, Expected Shortfall, backtesting and stress testing, applicable to any portfolio.
2. **An open-source Python implementation of my own BSc Finance dissertation methodology** (Part 2) — the Limited Expected Loss / Weighted Limited Expected Loss (LEL/WLEL) tail-risk extension and the regime-switching Hybrid Market-and-Climate VaR model, originally built in EViews for:

   > Semar, M. (2025). *"Bridging Two Worlds: A Comparative Analysis of Market VaR and Climate VaR Enhanced by Tail-Loss Metrics (LEL/WLEL)."* BSc Finance Applied Research Project, Bayes Business School. (Distinction, 80%)

The dissertation's EViews code only ever ran once, on two fixed stocks, for a course submission. This repository reproduces the same methodology as tested, reusable, open Python — runnable on any portfolio, any market data, on demand.

## Methodology

### Part 1 — General Market Risk Pipeline

**Volatility Forecasting.** Four approaches are compared on out-of-sample forecasting accuracy (RMSE, MAE, QLIKE loss): Historical (naive benchmark), EWMA (RiskMetrics-style), GARCH(1,1) (volatility clustering), and EGARCH (asymmetric leverage effect).

**Value-at-Risk & Expected Shortfall.** Three methodologies at 95% and 99% confidence: Historical Simulation, Parametric (normal or Student-t), and Monte Carlo (10,000+ simulated paths). Expected Shortfall is calculated alongside VaR since VaR answers "what is the loss threshold?" while Expected Shortfall answers "how severe are losses beyond that threshold?"

**Backtesting.** The Kupiec Proportion of Failures test checks whether the observed breach rate matches the model's stated confidence level; the Christoffersen independence test checks whether breaches cluster in time rather than occurring randomly — a sign a model fails to adapt during volatile regimes.

**Stress Testing.** Defined historical-replay and hypothetical scenarios (COVID-style crash, rate shocks) applied directly to portfolio weights.

### Part 2 — BSc Dissertation Methodology: Tail-Risk Extension & Climate VaR

**LEL and WLEL** (`src/tail_risk.py`). Standard VaR only tells you the threshold, not the severity of losses beyond it. Following Basak & Shapiro (2001), **Limited Expected Loss (LEL)** is the average loss conditional on being in the tail beyond VaR. **Weighted Limited Expected Loss (WLEL)** — the dissertation's own extension, following the weighting logic in Chen & Nguyen (2024) — up-weights the most extreme tail outcomes so rare, catastrophic losses aren't averaged away.

**Climate VaR** (`src/climate_var.py`). Estimates each asset's CAPM beta against the market, applies NGFS transition-scenario market shocks scaled by that beta, and runs Monte Carlo simulation to extract Climate VaR, LEL and WLEL per scenario.

**Hybrid Regime-Switching VaR** (`src/hybrid_var.py`). Blends short-horizon Market VaR with long-horizon Climate VaR by treating each simulated day as coming from a baseline market regime (probability 1 − p) or a climate-shocked regime (probability p, default 15%). See below for full details — this is the dissertation's central contribution, and the architectural template Part 3 reuses.

> Full source dissertation: Semar, M. (2025). *"Bridging Two Worlds: A Comparative Analysis of Market VaR and Climate VaR Enhanced by Tail-Loss Metrics (LEL/WLEL)."* BSc Finance Applied Research Project, Bayes Business School. (Distinction, 80%)

### Part 3 — Fusion: Earnings-Event-Conditional VaR (`src/earnings_signal.py`, `src/earnings_var.py`)

This is where the two dissertations meet, and the project's most original contribution.

**The idea.** The BSc dissertation's Hybrid VaR treats a *climate shock* as a regime that shifts the simulated return distribution on a given day. The MSc/Citibank dissertation independently built and rigorously validated a *continuous sentiment score* from earnings disclosures. Part 3 asks the natural next question: **what if a scheduled earnings event is treated the same way as a climate-shock regime** — using the disclosure's sentiment score to shift the simulated return distribution for that specific day, rather than assuming every trading day is statistically identical?

**The implementation.**
1. `earnings_signal.py` scores a disclosure's text for sentiment using a lexicon-based approach (Loughran-McDonald-style categories: positive, negative, uncertainty, litigious) — free, local, no API key required. It exposes a single `.score(text)` interface, specifically so it can be swapped for a real LLM call later without touching any downstream code — see the `LLMSignalScorer` stub in that file for the exact shape that upgrade would take.
2. `earnings_var.py`'s `event_conditional_var()` reuses the regime-switching mechanic from `hybrid_var.py`: the sentiment score shifts the expected return, and event-day volatility is inflated (reflecting the well-documented fact that earnings days carry more realised volatility than average days), before running the Monte Carlo VaR/LEL/WLEL calculation.

**The validation — the part that makes this a genuine contribution rather than a plausible-sounding gimmick.** Directly reproducing the Citibank dissertation's own evaluation standard rather than assuming the overlay works:
- `signal_return_correlation()` reproduces the dissertation's single strongest piece of evidence — a Spearman rank correlation between the sentiment score and the realised return, independent of any VaR threshold (the original found rho = 0.2565, p = 0.0001 on 109 real events).
- `backtest_event_overlay()` runs the same Kupiec and Christoffersen tests used throughout Part 1, but specifically comparing the sentiment-adjusted VaR against plain VaR **on earnings-event days only** — does the overlay actually produce better-calibrated exceedances, or does the added complexity not earn its keep?

**Honest framing, consistent with both source dissertations' own conclusions.** Neither original dissertation claimed its model should trade autonomously — the BSc dissertation called its hybrid model "illustrative rather than predictive," and the MSc dissertation's four-level trust framework placed autonomous trading at "not supported." Part 3 inherits that discipline: it is built and presented as a **risk model validation exercise** — does an earnings-aware overlay change, and specifically improve, VaR calibration around known event days — not as a trading signal. If `backtest_event_overlay()` shows no improvement on real data, that is the correct and useful conclusion to report, exactly as the Citibank dissertation reported honest null and mixed results (e.g. "score magnitude was found uncorrelated with accuracy") rather than only favourable ones.

> Full source dissertation: Semar, M. (2026). *"Reading Between the Lines: Can an LLM Predict How Markets React to Earnings?"* Citibank Applied Research Project, Bayes Business School.

### Part 4 — ML Volatility Extension: Does ML Actually Beat GARCH? (`src/ml_volatility.py`)

The optional extension from the original project plan, built deliberately last and treated as a genuine open question rather than an assumed ML win. A Random Forest and an XGBoost regressor are trained on lagged returns, lagged realised volatility, and rolling skew/kurtosis features, using a strictly chronological (non-shuffled) train/test split to avoid look-ahead leakage. Both are evaluated against the GARCH(1,1) baseline from Part 1 using the *same* RMSE / MAE / QLIKE metrics, for a fair comparison rather than a different yardstick for the "impressive" ML piece.

Consistent with this project's approach throughout: if GARCH wins, or the ML gap is small, that is the correct and more credible conclusion to report — a well-understood, parsimonious, regulator-accepted model beating a more complex one on a modest sample is a genuinely useful finding for a risk-team audience, not a disappointing result to bury.

## Data Notes

- `NGFS_SCENARIOS` in `src/climate_var.py` is **real data**, downloaded from the [NGFS Scenario Explorer](https://www.ngfs.net/ngfs-scenarios-portal/) (GCAM 6.0 NGFS model, World region, GDP|MER Counterfactual without damage, Phase 5 snapshot). GDP is used as a proxy for market-level impact, following Dietz et al. (2016)'s approach, since NGFS does not publish equity-index projections directly. Re-download for a newer scenario vintage if the NGFS portal updates.
- The `LEXICON` in `src/earnings_signal.py` is a small, hand-curated illustrative word list — not the full Loughran-McDonald Master Dictionary (free for academic use at [sraf.nd.edu](https://sraf.nd.edu/loughranmcdonald-master-dictionary/)). Swap it in for anything beyond a prototype.
- Sample earnings disclosures in `notebooks/08_earnings_event_overlay.ipynb` are generic, illustrative text written for demonstration — not real corporate filings or quotes.

## Deploying the Web App

To get a public, shareable URL (rather than only running locally):

1. Push this repository to your own GitHub account.
2. Go to [share.streamlit.io](https://share.streamlit.io) and sign in with GitHub.
3. Click "New app", select this repository, and set the main file path to `app.py`.
4. Deploy. Streamlit Community Cloud is free for public repos and gives you a URL like `https://your-app-name.streamlit.app` — a genuine link you can put on your CV or LinkedIn, not just a repo to clone.

Note: the deployed app will still need internet access to Yahoo Finance to download price data (works automatically on Streamlit Community Cloud); no API keys are required for the current lexicon-based earnings scorer.
